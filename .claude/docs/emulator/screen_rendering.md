# Screen Rendering

## Overview

The emulator renders the CRC-25R's 168 touchscreen screens from JSON definitions generated by the HTM parser. Each screen is a collection of absolutely-positioned widgets (buttons, text fields, images) with variable bindings and refresh triggers that control dynamic behavior.

## Screen Definition Format

Each screen is a JSON file in `frontend/public/screens/`:

```typescript
interface ScreenDef {
  name: string                           // Screen name (e.g., "MainScreen")
  filename: string                       // Source HTM filename
  resolution: { width: 800, height: 600 } // Always 800x600
  widgets: WidgetDef[]                   // Interactive/display widgets
  staticImages?: StaticImage[]           // Background images
  refreshTriggers?: RefreshTrigger[]     // Dynamic update rules
  initActions?: RefreshAction[]          // Actions on screen load
  hasFrenchVariants?: boolean            // Has French-language widgets
  memoryMap?: {                          // Variable documentation
    bytes?: Record<string, string>
    words?: Record<string, string>
    strings?: Record<string, string>
  }
}
```

## Widget Types

### Button (`type: "button"`)

```json
{
  "type": "button",
  "name": "btnDaily",
  "x": 8, "y": 470, "width": 72, "height": 47,
  "params": {
    "imageUp": "daily_up.png",
    "imageDown": "daily_down.png"
  },
  "bindings": [
    {"source": "internalRAM", "type": "byte", "index": 189, "param": "setValue"}
  ],
  "language": "english"
}
```

- Renders up/down button images from `/assets/images/`
- On click: sends `buttonPress` with the bound byte index and value
- `language` field controls visibility based on byte(100)

### Text Field (`type: "textfield"`)

```json
{
  "type": "textfield",
  "name": "sfActivity",
  "x": 180, "y": 200, "width": 427, "height": 114,
  "params": {
    "font": "Arial Black Bold",
    "fontSize": "72",
    "color": "#000000",
    "align": "right"
  },
  "bindings": [
    {"source": "internalRAM", "type": "string", "index": 10, "param": "value"}
  ]
}
```

- Displays the value of the bound string variable
- Updates in real-time as the firmware sends new values
- Font, size, color, and alignment from params

### Image (`type: "image"`)

```json
{
  "type": "image",
  "name": "imgLogo",
  "x": 0, "y": 0, "width": 800, "height": 69,
  "params": {
    "src": "header_bar.png"
  }
}
```

- Renders a static image at the specified position
- Sources from `/assets/images/`

### Bar Graph (`type: "bargraph"`)

```json
{
  "type": "bargraph",
  "name": "bgSpectrum",
  "x": 50, "y": 100, "width": 700, "height": 300,
  "bindings": [
    {"source": "internalRAM", "type": "word", "index": 50, "param": "value"}
  ]
}
```

- Renders bar chart from word variable data
- Used for MCA spectrum display and activity graphs

### Function Button (`type": "functionbutton"`)

Similar to button but styled for function key rows (F1-F8 in navigation bars).

## Refresh Triggers

Refresh triggers define dynamic behavior — how the screen responds to variable changes.

### Structure

```typescript
interface RefreshTrigger {
  name?: string          // Trigger identifier (for forceUpdate matching)
  interval?: string      // Time-based refresh (not commonly used)
  onVar?: string         // Variable to monitor: "byte(20)", "word(5)"
  trigger?: string       // Value that activates: "255", "0"
  actions?: RefreshAction[] // What happens when triggered
}
```

### Action Types

```typescript
interface RefreshAction {
  type: string           // Action type
  target?: string        // Widget name or trigger name
  value?: number | string // Value for setValue actions
  macro?: string         // Amulet macro (for complex actions)
  args?: string          // Macro arguments
}
```

| Action Type | Description | Example |
|-------------|-------------|---------|
| `reappear` | Show a widget | `{"type":"reappear","target":"btnHome"}` |
| `disappear` | Hide a widget | `{"type":"disappear","target":"btnHome"}` |
| `setValue` | Set a byte/word value | `{"type":"setValue","target":"byte(20)","value":0}` |
| `forceUpdate` | Re-evaluate another trigger | `{"type":"forceUpdate","target":"refreshShowHome"}` |

### Trigger Evaluation

When a byte or word value changes, the `ScreenRenderer` evaluates all triggers:

1. Check if `onVar` matches the changed variable (e.g., `byte(20)`)
2. Check if `trigger` value matches the new value
3. If match, execute all `actions` in order
4. For `forceUpdate` actions, find triggers by name prefix and evaluate them

### Toggle vs State Triggers

**Toggle triggers** have a `setValue` action that resets the byte back to a base value. They represent one-shot events (e.g., "refresh all widgets now"):

```json
{
  "name": "refreshChambString",
  "onVar": "byte(20)",
  "trigger": "255",
  "actions": [
    {"type": "reappear", "target": "sfChamb"},
    {"type": "forceUpdate", "target": "refreshShowHome"},
    {"type": "setValue", "target": "byte(20)", "value": 0}
  ]
}
```

**State triggers** respond to static state (e.g., "if language is English, show English buttons"):

```json
{
  "name": "refreshShowHomeEnglish",
  "onVar": "byte(80)",
  "trigger": "0",
  "actions": [
    {"type": "reappear", "target": "btnHome"}
  ]
}
```

### forceUpdate Chain

`forceUpdate` creates chains by matching trigger names by **prefix**:

```
forceUpdate("refreshShowHome") matches:
  - "refreshShowHomeEnglish" (byte(80)=0 → reappear btnHome)
  - "refreshShowHomeFrench"  (byte(80)=1 → reappear btnHomeFrench)
```

Only the trigger whose byte value matches the current state fires.

### Initial Replay

On screen load, the renderer performs an initial trigger replay:

1. Only fires **toggle triggers** (those with `setValue` actions)
2. Checks if the trigger's byte matches its current value
3. Executes actions including `forceUpdate` chains
4. State triggers are reached via `forceUpdate` from toggle triggers

This prevents a show+hide conflict where both English and French visibility triggers fire sequentially (the last one would always win).

## Page Navigation

### Page Map (`screen_map.json`)

Maps firmware page indices to screen names:

```json
{
  "9": "MainScreen",
  "16": "Daily",
  "17": "Background",
  "18": "ChamberVolts",
  "20": "Accuracy",
  "25": "Setup"
}
```

### Navigation Flow

1. Firmware sets byte(3) to the target page via `SetAmuletHTML()`
2. Bridge broadcasts `{"type": "setPage", "page": N}`
3. `ScreenRenderer` receives page change via `stateManager.onPageChange`
4. Calls `loadScreenByPage(N)` to fetch JSON definition
5. Renders new screen's widgets and evaluates initActions + triggers

### Screen Caching

Screen definitions are cached in memory after first load. Navigating back to a previously visited screen does not re-fetch the JSON.

## Language Support

### Dual Widget Sets

Screens with French support have paired widgets:

```json
[
  {"type": "button", "name": "btnDaily", "language": "english", ...},
  {"type": "button", "name": "btnDailyFrench", "language": "french", ...}
]
```

### Language Byte

- `byte(100)` = 0: Show English widgets, hide French
- `byte(100)` = 1: Show French widgets, hide English

### Visibility Control

The refresh trigger system manages language visibility:

```json
{
  "name": "refreshShowHomeEnglish",
  "onVar": "byte(80)",
  "trigger": "0",
  "actions": [{"type": "reappear", "target": "btnHome"}]
},
{
  "name": "refreshHideHomeEnglish",
  "onVar": "byte(80)",
  "trigger": "1",
  "actions": [{"type": "disappear", "target": "btnHome"}]
},
{
  "name": "refreshShowHomeFrench",
  "onVar": "byte(80)",
  "trigger": "1",
  "actions": [{"type": "reappear", "target": "btnHomeFrench"}]
}
```

The firmware sets `byte(80) = current.language` when entering each screen.

## HTM Parser

### Source

`tools/htm_parser/parse_htm.py` (Python 3, requires BeautifulSoup4)

### Input

168 Amulet `.htm` files from `firmware/CRCHtml_3.00a/`

### Parsing

Extracts from each HTM file:

1. **Memory map** from HTML comments (byte/word/string variable bindings)
2. **Widgets** from HTML elements:
   - Position: `style="position:absolute;left:X;top:Y;width:W;height:H"`
   - Button images: `SRC="Images/filename.png"`
   - Variable bindings: `Amulet:internalRAM.byte(N).value()`
   - Click actions: `Amulet:internalRAM.byte(N).setValue(V)`
3. **Refresh triggers** from META REFRESH tags:
   - ONVAR conditions
   - Actions (reappear/disappear/forceUpdate)
4. **Static images** from background and layout elements

### Output

- `frontend/public/screens/{ScreenName}.json` — One per screen
- `frontend/public/screen_map.json` — Page index to screen name mapping

### Regenerating

```bash
cd tools/htm_parser
pip install beautifulsoup4
python parse_htm.py
```

## Screen Layout Conventions

The 800x600 display follows a consistent layout:

| Region | Y Range | Content |
|--------|---------|---------|
| Header | 0-69 | Title bar, Home/Back buttons |
| Content | 70-469 | Screen-specific widgets and data |
| Footer | 470-600 | Navigation tabs, chamber indicator |

### Navigation Bar

Bottom row buttons (y ~470-520):
- Daily, Background, ChVolt, Accuracy, Enhanced, Moly, Inventory, Util
- Each has English and French image variants

### Home/Back Buttons

Top-right area (~x:710-790, y:0-60):
- Visible on all screens except MainScreen
- Controlled by byte(20) trigger chain → forceUpdate → language visibility
